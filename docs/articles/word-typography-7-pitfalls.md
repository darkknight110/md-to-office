# 中文 Markdown 转 Word，90% 的人卡在这 7 个排版细节

上个月给一份仓储方案排 Word。同事打开后问了一句：「字怎么跟我原来那版不一样？」

我查了半天才发现：转换器里我设了正文字体，但只设了西文那一栏。中文走的是另一套属性，根本没变。

后来我把手上 52 份交付物（方案、报告、验收记录）逐份量了一遍：正文 10.5pt、行距 1.15 倍、页边距 22-22-20-20mm——**52 份一模一样**。没有人调过，默认值就是事实标准。而它离国标公文（16pt 仿宋、28 磅行距、版心 156×225mm）差了整整一个量级。

下面 7 个坑，都是量出来或踩出来的。每个说清：什么症状、为什么、怎么改。

## 坑 1：只改「字体」，中文其实没变

在 Word 里把字体改成「思源宋体」，正文还是原来的宋体，标题倒是变了——因为 Word 的字体分两套：西文（`w:ascii` / `w:hAnsi`）和东亚（`w:eastAsia`）。多数 Markdown 转 Word 的库只设 `ascii`，中文走的是 `eastAsia`，所以中文没被改到。

查法很直接：把 docx 解压，看 `word/document.xml`：

```xml
<w:rFonts w:ascii="Times New Roman" w:eastAsia="宋体"/>
```

**`eastAsia` 才是中文的字体**。Word 里的入口是「开始 → 字体 → 中文字体」；写代码就必须显式设 `w:eastAsia`。

## 坑 2：字号不是像素，是「半磅」

以为「三号字 = 16px」，按 16px 设，打印出来比公文小一圈。

Word 的字号单位是半磅（half-point）：`w:sz="32"` 是 16pt，不是 32pt。中文里三号 = 16pt，小四 = 12pt，五号 = 10.5pt。

常用的几个换算：

| 中文字号 | pt | Word XML `w:sz` |
|---|---|---|
| 二号 | 22 | 44 |
| 三号 | 16 | 32 |
| 小三 | 15 | 30 |
| 四号 | 14 | 28 |
| 小四 | 12 | 24 |
| 五号 | 10.5 | 21 |

别按「看起来差不多」调，按 pt 设。

## 坑 3：行距「1.15 倍」和「28 磅」不是一回事

公文要求行距 28 磅。你在 Word 里选「1.5 倍行距」，打印出来不是 28 磅，因为倍数行距随字号变，固定值不随字号变。

1.15 倍 × 10.5pt ≈ 14.5pt，这正是我们那 52 份交付物的实测值；而公文要的是固定 28 磅，与字号无关。为什么公文要固定值？因为「每面 22 行」是硬规定，只有固定行距才数得出来。

Word 里选「段落 → 行距 → 固定值 28 磅」；代码里是 `lineRule="exact"`、`line=560`（1pt = 20 twips，28pt = 560 twips）。

## 坑 4：首行缩进 2 字符，别用两个空格

用两个全角空格缩进，换台电脑、换个字体就歪了。空格宽度依赖字体，而「首行缩进 2 字符」是段落属性，Word 会按当前字号自己算。

Word 里设「段落 → 特殊格式 → 首行缩进 2 字符」；代码里是 `w:ind w:firstLine="640"`（2 字符 × 16pt = 32pt = 640 twips）。

## 坑 5：页边距不是「留白好看」，是版心契约

把页边距调成 2cm 觉得紧凑好看，结果每行字数、每页行数全变了。

公文真正规定的不是边距，是版心 156×225mm：天头 37、下白边 35、订口 28、右白边 26（毫米），正文 3 号仿宋，每面 22 行、每行 28 字。

而这两个数字不是拍脑袋：156mm = 442pt，442 ÷ 16 ≈ 27.6，取 28 字；225mm = 638pt，638 ÷ 28 ≈ 22.8，取 22 行。版心 ÷ 字号 ÷ 行距 = 行列数，三个参数互相锁死。所以顺序是：先定版心，再定字号，最后用行距凑行数。

## 坑 6：表格是排版的重灾区

表格跨页后表头不见了；合并单元格一多，脚本读出来列全错位；表格里的数字带千分位，求和直接变 0。

这三件事在 Word 里是三个独立开关：表头重复要勾「重复标题行」；合并单元格在视觉上没问题，但 pandas 和 openpyxl 会把列名读成 `Unnamed`；`12,000` 是字符串不是数字，求和不会报错，只会算成 0。

一个不花钱的自查：把「合计行」当校验和，明细求和跟合计行对一遍，对不上就说明有一方错了。

## 坑 7：ASCII 字符画，转成 Word 必错位

在编辑器里对齐得好好的架构图，一进 Word 就散架。

原因是字符画依赖两个前提：等宽字体、每个字符占一格。Word 用比例字体，而中文字符占 2 格。两个前提同时不成立，换什么字体都救不回来。

我们做这个工具时，最早的版本试过「给字符画套一个等宽字体」，结果只是错得整齐一点。后来改成：用 JSON 描述层次，渲染成 PNG 再插进去。

```json
{
  "diagrams": [{
    "out": "arch.png",
    "top": { "title": "小程序前端", "sub": "四种场" },
    "main": { "title": "业务内核", "modules": [["知识库", "生产管线"], ["限流", "兜底"]] },
    "bottoms": [{ "title": "AI 能力层" }, { "title": "云开发" }]
  }]
}
```

图是资产，不是字体的副产品。

## 一张自查表

| 检查项 | 合格线 | 怎么快速确认 |
|---|---|---|
| 中文东亚字体 | 与西文分开设置 | 解压 docx 看 `w:eastAsia` |
| 字号 | 按 pt/字号表，不按像素 | `w:sz` 是半磅 |
| 行距 | 公文用固定值 28 磅 | `w:lineRule="exact"` |
| 首行缩进 | 2 字符（段落属性） | `w:firstLine="640"`（16pt 时） |
| 版心 | 156×225mm（公文） | 边距 37/35/28/26 |
| 表格 | 表头重复、数字是数值 | 求和一次看是否为 0 |
| 字符画 | 不出现在成品里 | 搜 `┌ └ │` |

## 这些数从哪来

52 份真实交付物的实测：中位 3,517 字、12 个二级章节、182 行表格；正文 10.5pt、行距 14.5pt、边距 22-22-20-20mm，52 份完全一致。国标那组来自 GB/T 9704-2012。量测脚本和原始数据都开源，可以拿自己的文档目录复跑：`python3 tools/measure_typography.py --out baseline.json <你的目录>`。

我用这套规范写了个转换工具 md-to-office：`md2office --input 方案.md --format docx`，会把字符画按 spec 换成真图。但上面 7 条结论不依赖它，你用任何工具都该核对。
