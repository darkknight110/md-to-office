# 中文排版基线：把「默认宋体小四」换成可核对的数字

> **一句话**：这套工具 52 份真实交付物的版式**完全一致**（10.5pt / 1.15 倍行距 / 22-22-20-20mm），
> 说明默认值事实上就是"家规"；而它离国家公文规范（16pt / 28pt / 37-35-28-26mm）差得很远。
> 这两个事实都是量出来的，不是感觉出来的。

- 机器可读：**[`docs/typography-baseline.json`](typography-baseline.json)**
- 复跑方式：`python3 tools/measure_typography.py --out baseline.json <目录或文件...>`

---

## 一、为什么要有基线

排版争议通常长这样："正文用 10.5 还是 12？行距 1.15 还是 1.5？"
两边都没有依据，最后比谁声音大。基线把这个问题变成**测量问题**：

1. 先量**现状**（我们自己产出的文档实际是什么参数）；
2. 再引**规范**（对外交付有硬性要求的，引国标原文）；
3. 最后写**差距**（哪几项差、差多少、影不影响交付）。

有了这三层，"我默认宋体小四"就从**偏好**变成**有据可依的选择**，或者变成一个**已知偏差**。

---

## 二、量了什么，怎么量的

| 维度 | DOCX（精确值） | PDF（估计值） |
|---|---|---|
| 来源 | OOXML 声明：`sectPr` 页边距、run/style 字号、Normal 行距 | pdfplumber 字符包围盒 |
| 字号 | 各 run 真实字号，按字符数加权取众数 | 同左，但受表格小字影响 |
| 行距 | Normal 样式声明值（倍数或磅值） | 整行宽相邻行的基线间距中位数 |
| 页边距 | 声明值 | **不可靠**：量到的是文本包围盒，页眉页脚会污染（实测下边 12.9mm 是页码位置） |

**样本**：`项目方案/` 下的 52 份 DOCX + 18 份 PDF（中原四季、成语小程序、今天吃啥不麻烦等真实对外交付物）。
**这不是行业抽样**——它回答"我们的现状"，不回答"行业普遍"。这一点必须说清楚，否则基线就是新的自欺。

## 三、实测结果

### 3.1 现状（business-report，n=52）

| 参数 | 值 | 备注 |
|---|---|---|
| 页面 | A4 210×297mm | — |
| 正文字号 | **10.5pt**（五号） | 52/52 一致 |
| 表格字号 | 9.0pt | 同上 |
| 标题字号 | 15 / 13 / 11.5pt | H1/H2/H3 |
| 行距 | **14.5pt**（1.15 倍） | = 1.15 × 10.5 × 1.2 |
| 段后 | 4pt | — |
| 页边距 | **22 / 22 / 20 / 20mm** | 上/下/左/右 |
| 版心宽 | 170mm | 210 − 20 − 20 |
| 每行字数（估） | ≈46 字 | 481.9pt ÷ 10.5pt |
| 每页行数（估） | ≈49 行 | 717.2pt ÷ 14.5pt |

**最值得注意的一条**：52 份文档**零差异**。没有人手工调过字号或边距——
默认值就是这套文档的事实标准。这既是好事（一致性极高），也是风险（默认值错了，52 份一起错）。

### 3.2 规范（gongwen，GB/T 9704-2012）

| 参数 | 规范值 |
|---|---|
| 页面 | A4 210×297mm |
| 页边距 | **37 / 35 / 28 / 26mm**（天头/下白边/订口/右白边） |
| 版心 | 156×225mm（不含页码） |
| 正文字体 | 3 号仿宋（**16pt**） |
| 行距 | **28pt** |
| 每面 | **22 行 × 每行 28 字** |

**交叉验算**（这一步能证明规范不是拍脑袋）：
- 版心宽 156mm = 442.2pt，442.2 ÷ 16 ≈ **27.6 → 28 字/行**；
- 版心高 225mm = 637.8pt，637.8 ÷ 28 ≈ **22.8 → 22 行/面**。

即：`22 行 × 28 字` 是"版心尺寸 ÷ 字号 ÷ 行距"的必然结果，不是经验数字。

### 3.3 差距

| 项 | 我们 | 规范 | 比值 | 后果 |
|---|---|---|---|---|
| 正文字号 | 10.5pt | 16pt | 0.66 | 长文阅读疲劳；不符合公文硬性要求 |
| 行距 | 14.5pt | 28pt | 0.52 | 页面密度接近两倍 |
| 天头 | 22mm | 37mm | — | 装订与签批空间不足 |
| 订口 | 20mm | 28mm | — | 双面打印装订后文字易被吃掉 |
| 每行字数 | ≈46 | 28 | 1.64 | 行长过长，换行回溯成本高 |
| 每页行数 | ≈49 | 22 | 2.23 | 单页信息量翻倍 |

## 四、结论：分场景，不搞一刀切

1. **内部方案 / 研报 / 技术文档：保持现状（10.5pt / 1.15 / 窄边距）。**
   公文规范是为"红头文件 + 装订 + 领导签批"设计的，套到内部技术方案上只会浪费纸张和信息密度。
2. **对外正式公文 / 需要盖章报送的材料：必须切到 gongwen 参数。**
   现状与规范差 2 倍以上，不是"风格问题"，是"不合规"。
3. **`gongwen` 目前只是数字，不是功能。**
   本仓库**尚未实现**该 profile（需要新增 Config 预设、页码/页眉格式、以及仿宋_GB2312 的字体回退方案）。
   在 `typography-baseline.json` 里它被明确标成 `"not_implemented"` —— 不声称未完成的能力。

---

## 五、边界（必须一起读）

- **样本是自有交付物**，不含外部机构文档；要行业基线，得另做外部采集。
- 外部 PDF 在本机网络下大面积不可达（`raw.githubusercontent.com` 连接重置、部分政务站点 403/449），
  因此**没有**混入"看起来像外部基线"的样本。
- PDF 的页边距是文本包围盒，**不等于**版面声明值；只用来交叉验证字号与行距。
- 行距只统计"整行宽"的相邻行，表格密集页会被排除。

> 更新方式：`python3 tools/measure_typography.py --out docs/typography-baseline.json "项目方案"`，
> 然后对照本页核对三段结论（现状 / 规范 / 差距）是否需要改写。
